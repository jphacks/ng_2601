# AIエージェント共通開発規約

人間とAIが、過去のチャット履歴なしで同じIssueを引き継ぐための規約です。特定のAI、外部サービス、常駐プロセスは必要ありません。

## 作業開始時

1. [README](../README.md)でプロジェクト概要、[開発参加案内](docs/README.md)で資料の役割を確認する。
2. [アーキテクチャ](docs/architecture.md)、[API契約の案内](docs/api-contract.md)、対象機能の仕様・必要な[ADR](docs/decisions/README.md)を読む。
3. [対象Issue](https://github.com/jphacks/ng_2601/issues)の受入条件、依存Issue、[関連PR](https://github.com/jphacks/ng_2601/pulls)の差分・レビュー・マージ状態を確認する。未マージの内容を採用済みとして扱わない。
4. 関連する[Handoff](docs/handoffs/README.md)と実装を読み、既存機能や進行中の機能を重複実装しない。
5. `git status --short --branch`、`git diff`、`git diff --cached`、`git worktree list`で現在の変更と作業場所を確認する。既存の未コミット変更を消去・混入させない。担当Issueごとに専用ブランチを使い、並行作業では別worktreeを推奨する。
6. Issueの担当者・関連PRから作業範囲を確認する。担当者欄が空でも未着手とは限らない。共有ファイルを編集する前に担当者と調整する。不明な仕様は未決定と記録し、関係者に確認する。確認待ちの間は独立した作業を進める。

## 実装時

- Issueのスコープを守り、無関係なリファクタリングや機能追加をしない。
- API契約を無断で破壊しない。変更案はFE・BE双方と調整し、[更新手順](docs/api-contract.md)に従う。
- 他担当者の変更を上書きしない。特に共通の型、API client、依存関係のlockfileは編集範囲と取り込み順を調整する。競合時は双方の意図を確認し、片側を一括採用しない。
- `reset --hard`、`clean`、他人の変更の破棄、共有ブランチへのforce pushを独断で実行しない。
- 新規依存パッケージには必要性・代替案をPRで示す。既存のビルド・テスト手順とlockfileを尊重し、存在しないコマンドや設定を推測で追加しない。
- 確認済みの実装、Issue上の要件、PR内の提案、未決定事項を区別する。文書が食い違う場合は[正本と矛盾の解決方法](docs/README.md)に従う。

## 作業完了・中断時

- 変更点と理由、主要ファイル、実行した検証コマンド・実行場所・結果をPRに残す。失敗、未実施、既知の制約も明示する。
- [Handoff作成条件](docs/handoffs/README.md)を確認し、必要なら[TEMPLATE](docs/handoffs/TEMPLATE.md)から記録する。小規模変更はPR本文でよい。
- 設計を変更したらアーキテクチャとAPIの正本・参照を更新する。重要な意思決定だけADRに残す。過去の判断を推測で後付けしない。
- [PRテンプレート](../.github/pull_request_template.md)を使い、関連Issue・更新文書・必要なHandoffをリンクする。別Issueを誤って閉じるキーワードを付けない。
- 中断時はブランチ、保存済みコミット／未コミット差分、失敗した受入条件、再開の最初の操作を残す。次担当はHandoffの時点と現在の差分を確認して再開する。

## 禁止事項

- リポジトリ直下の`README.md`を編集・削除・移動・改名・自動整形すること。AIは閲覧のみとし、開発参加案内や開発手順の追記・更新は[docs/README.md](docs/README.md)または該当する機能別ドキュメントで行う。
- テストしていない内容を成功と報告する。
- 存在しないAPIや実装を既存機能として記載する。
- 秘密情報・認証情報・個人の位置情報・不要な会話ログをコミット、ログ、ドキュメントに記録する。
- 明示的な指示なしにmainへ直接pushする、またはPRをマージする。

文書と検証結果は簡潔に残し、同じ情報を複数箇所で独立管理しない。
