# 実装引き継ぎ

Handoffは「何を変え、何を確かめ、何が残り、次に何をするか」を作業時点の記録として残します。最新仕様は[アーキテクチャ](../architecture.md)と[APIの正本](../api-contract.md)、最新のタスクはIssueで確認します。古いHandoffはそれらを上書きしません。

## 作成条件

| 条件 | 扱い |
| --- | --- |
| 未完成のまま担当者・AIが交代する | 必須。未保存／未コミットの状態、ブロッカー、再開手順も記録する |
| 複数人・複数AIにまたがり、PR本文だけでは次作業が判断できない | 必須。依存する作業・編集範囲・取り込み順を記録する |
| 大きな機能、アーキテクチャ変更、重要な未解決問題がある | 推奨。次担当が迷う継続作業があれば作成する |
| 小規模修正・誤字修正・単独で完結する変更 | 個別ファイルは不要。[PRテンプレート](../../../.github/pull_request_template.md)の検証・残課題を引き継ぎ記録にする |

## 作り方・読み方

1. [TEMPLATE.md](TEMPLATE.md)を`YYYY-MM-DD-issue-N-short-topic.md`としてコピーする。Issueがなければ`YYYY-MM-DD-short-topic.md`でよい。
2. Metadataに更新日、Issue、PR、ブランチ、基準コミットと保存状態を記す。Statusは`進行中 / 中断 / レビュー待ち / 完了`等。完了はマージ済みを意味しない。該当しない欄は理由とともに記す。
3. Changesは実際の変更だけを書く。PRやADRに詳細があればリンクし、同じ説明を複製しない。Verificationは実行場所・コマンド・結果と未実施を分ける。
4. Next Actionsを順番に書き、担当範囲・依存するPR・未合意事項があればリンクする。会話の経緯を知らなくても最初の一手が分かるようにする。
5. PR本文からHandoffをリンクする。継続作業のIssue側でもPR／Handoffを辿れるようにする。交代時は共有できるブランチに保存し、ローカルにしかない差分を共有済みとして扱わない。
6. 次担当はこの案内 → 対象Handoff → 参照先の最新仕様・Issue／PR → ブランチと差分、の順に確認する。古い失敗や未解決事項が既に解消されていないか照合する。

同じ作業を継続する場合は既存Handoffを更新し、別の作業を始める場合だけ新規作成します。一覧表を別管理せず、[このディレクトリ](.)のファイルと関連PRから探します。
